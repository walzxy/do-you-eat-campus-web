# 数据模型

## 实体关系

食堂 (1) --< 窗口 (1) --< 菜品

食堂 一对多 窗口
窗口 一对多 菜品

## 关键设计

1. 食堂、窗口、菜品均有唯一编号
2. 窗口编号全校唯一，不重复使用
3. 同名菜品在不同窗口/食堂使用不同菜品编号
4. 菜品关键词独立于菜品名称，支持大类搜索
5. 供应状态区分已核实和未核实，不掩盖不确定性

## 供应状态

- 已核实售卖：实地确认当前有售
- 菜单记录，未核实：出现在菜单上但未确认
- 可能售卖：根据窗口菜品大类推断
- 暂时未售卖：确认当前未售，但后续可能恢复
- 已停止记录：确认不再售卖
- 未知：信息不足

## 账号与社区实体

账号和社区数据使用独立存储配置：本地开发默认写入 `data/community/*.json`，云函数部署通过 `SOCIAL_STORAGE=cloudbase` 写入云开发数据库。当前集合/文件名为：

- `accounts`：匿名 ID、昵称、头像、未来登录提供方和提供方用户标识
- `tastes`：固定口味标签、主动避开项
- `meal_history`：饭录及菜品快照，支持 `client_id` 幂等同步
- `posts`：文字内容、可选菜品快照、点赞/收藏/评论计数
- `comments`：帖子评论，使用 `parent_id` 表示任意层级回复
- `reactions`：点赞和收藏关系
- `notifications`：点赞、收藏、评论、回复通知
- `ratings`：匿名账号对菜品的 1–5 星评分

注销账号时，个人资料、口味、饭录、互动、评分和通知会清理；帖子和评论不删除，而是保留内容并将作者改为“已注销用户”。这样既满足账号删除，也避免社区讨论出现断链。
